# WorkBuddy 与豆包工作：工具证据和命令诊断

## 已核实

- Connector 当前服务只处理 `claim_next_task`、`submit_result`、`report_blocked`，事件记录本服务收到的调用和响应；不会自动订阅客户端内部终端工具。见 [Connector 实现](../connectors/workbuddy-eval/server.mjs) 和两次 [运行记录](../../runs/复核/2026-11-24-E8-办公产品运行记录.md)。
- 两次结果中的命令返回来自产品提交的报告或 agent summary；不能当成独立采集的原始工具日志。豆包工作本机发现对应的文件变更快照，只记录产物文件的 Write 等信息，不含本次命令的原始工具返回。
- WorkBuddy 报告表示结果为 exit 1 / SIGTERM、目标状态文本未出现；这不证明原因是某种 shell、权限、工作目录、超时或路径问题。豆包工作报告表示返回 exit 23 和两行状态文本；需要原始工具记录复核。

## 用户提供的 WorkBuddy 界面记录

用户展开界面后提供：第一次 Bash 调用 `cd` 到本次任务 workspace 并输出该目录；第二次独立 Bash 调用 `cmd.exe /d /c tools\\\\ok_then_fail.cmd`，显示 Windows 横幅及 `f:\\test\\workbuddy>` 提示符，最终报告退出码 1。用户粘贴的目录文字可能有识别误差，以原始界面为准。

可以确认两次是独立工具调用，第二次没有看到预期的两行文本。**待验证假设**：工具调用的工作目录不跨调用保持、Windows `cmd.exe` 的参数/交互方式或进程管理造成未执行夹具。横幅和提示符不能单独证明准确工作目录或 SIGTERM 根因；不能把猜测记成已修复。

优先诊断：使用独立非基准任务，先确认单次工具调用实际工作目录与参数，再检查工具是否提供独立 `workdir` 参数和进程结束信息。若不支持设置工作目录，再讨论带显式目录的 Windows 等效任务，作为不同版本记录；不得擅自在原 E8 命令中追加 `cd` 或包装命令并仍称其为原题条件。

### 独立诊断反馈

用户提供 WorkBuddy 独立 Bash 调用结果：第一条 `cd / && pwd` 返回 `/`；下一条单独执行 `pwd` 返回 `/f/test/workbuddy`。这支持本次环境的工作目录不跨调用保持。第三条 `cmd.exe /d /c echo HARNESS_DIAG_OK` 显示 Windows 横幅和交互提示符，未出现标记，报告 exit 1 / SIGTERM。MSYS 参数转换是可能原因，但尚未通过对照实验验证。以上为用户转述客户端展示的结果，不是由评测侧独立采集的工具事件。

下一步在独立诊断对照 `MSYS_NO_PATHCONV=1` 或双斜杠参数；如有效，也只能说明这条诊断命令的行为。使用不同命令形式、合并目录切换或更改进程环境都需要清楚标注条件，不能直接算原 E8 命令已通过。

### MSYS 对照结果

用户转述 WorkBuddy 两次独立 Bash 工具调用：`MSYS_NO_PATHCONV=1 cmd.exe /d /c echo HARNESS_DIAG_OK` 和 `cmd.exe //d //c echo HARNESS_DIAG_OK` 均输出预期文本并以 0 退出；未加调整的同类命令显示交互提示并被终止。该对照支持 MSYS 参数转换是此前命令异常的原因，但未独立观察进程实际接收的参数，也未证明 E8 夹具在调整条件下已执行。

修复需要同时处理工作目录不跨调用保持与参数转换。优先验证产品命令工具是否支持为单次调用设置工作目录、能否从客户端会话配置 `MSYS_NO_PATHCONV=1`；若只能在命令中使用前缀、`cd` 或双斜杠，应作为独立适配题版本运行和评分，保留与原始命令的差别。原 E8 运行保持不变。

## 修复方向

1. 先保留每款产品对话中本次命令的原始展示：工具名、完整入参、工作目录、输出、退出码、终止状态和时间。人工复制或导出须标明来源和操作者；不重新执行，不改写原 run。对 UI 展示或人工复制的内容不要标为服务端独立 Trace。
2. 查证两个客户端是否有官方可用的工具事件或会话导出接口；若支持，适配器保存与 run 对应的原始事件和 SHA-256。不能从 Connector 现有日志自动推断客户端工具事件完整性。
3. 如接口不开放，可让产品在新一轮主动提交工具输出或由操作者导出，再归档为 `agent_reported` / `operator_exported`；这能提高可检查性，但仍需保留来源限制。不要改变原题的原生命令、禁止查看脚本或单次调用约束来制造“通过”。
4. WorkBuddy 单独建立非基准诊断任务，逐步检查当前终端类型、工作目录、执行参数和进程生命周期；每步分开记录，不把诊断命令混入 E8 正式轨迹。依据实际原始工具记录再确定修复，修复后新建 run 验证。

两种诊断结论均不溯及旧 run；Connector 的工具事件和客户端内部操作属于不同观测层。
