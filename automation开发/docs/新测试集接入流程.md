# 新测试集接入流程

适用于通过 Runner 接入新公开测试集或新任务。每次先完成题目、评分和证据准备，再试跑；各产品的适配程度和试跑结果分别记录。

## 1. 确定测试集和题目

1. 明确要观察的能力，筛选题目：任务目标、输入、输出、环境和官方评分是否能取得并理解。
2. 记录来源、许可及使用限制、测试集版本、commit 或发布版本、题目 ID；对输入、提示词和评分器记录 SHA-256。输入暂不可得时记待核实。
3. 检查各产品能否取得输入、访问任务环境和交回产物；区分产品能力未知、接入阻塞和实际任务失败。
4. 写清任务合同：输入路径、提示词、允许的工具/权限、环境、目标产物和超时。路径或环境发生变更时记录改编，不把子集或改编结果称作完整官方基准成绩。
5. 按现有 Runner 合同准备 `cases/public/<dataset>-<task>/case.json` 与必要材料。当前 Runner 每次准备一个 `input_source`；多输入需先确认支持方式，不要假设自动展开。答案、评分脚本及凭据留在评测侧，避免提供给被测产品。

**完成条件**：题目及输入来源可追溯、合同可执行、各产品接入条件和未知项明确。

## 2. 准备独立评分

1. 阅读官方评分实现及依赖，列出每项检查、分值、可接受格式及可能的误判。固定评分版本；官方评分无法使用时，明确注明独立实现及差异。
2. 评分器只读取归档的 run、case、trace 和产物；核对 run ID、case 摘要、产物路径及哈希。评分输出放新目录，不覆盖原始运行。
3. 先用人工准备的正例、错误答案、缺失产物和损坏摘要检查评分器；可能存在多种正确答案时准备对应反例。若依赖 LLM Judge，记录模型和提示词版本。
4. 分开记录归档状态、每项得分、任务结果及证据不足；不要将评分器错误或环境阻塞记为产品任务失败。
5. 确认评分器能否由单次 Runner 或批次调用。尚未接入时记录独立执行命令，不声称自动评分已接通。

**完成条件**：评分规则、依赖和版本明确，正负例检查通过，运行及阻塞状态可追溯。

## 3. 准备 Trace 与证据采集

先为每个产品填写：入口、可用日志、工具调用及返回能否取得、产物与配置如何归档、是否需要人工操作、覆盖范围及未知项。日志格式可能随版本改变，应使用该产品实际产生的记录验证。

- Runner 的 `run.json`、`trace.json` 和产物摘要记录运行与归档；不自动代表完整内部轨迹。
- Codex/DSH 可检查 CLI 原始事件；WorkBuddy/豆包工作的 Connector 日志记录队列边界，客户端工具事件需要另行采集和验证。
- 保存必要原始证据，记录路径、摘要、事件定位和采集方式；脱敏时保留可复核性，避免归档凭据与无关私人内容。
- 新题使用已有转换器前先核对适用范围。E8 专用解析器不能直接当作任意任务的 Trace 采集器。覆盖不足写 `unknown`。
- [运行证据索引器](../runner/index-run-evidence.mjs)可索引 Runner 已声明的证据，但不会采集缺失的客户端工具事件。

**完成条件**：每款产品明确“可采集、已实测、未知或阻塞”；关键证据能回溯到具体运行。无法获得的过程证据保留未知，不阻止有明确范围的产物预实验。

## 4. 试跑及决定是否批量运行

1. 先用一款已接入产品完成任务交付、执行、全部产物回收、独立评分及证据归档；检查运行失败时的状态。
2. 再逐款确认实际接入、人工领取步骤、产物和可见事件。保留失败、超时及重跑记录，每次使用新 run ID。
3. 根据试跑修订合同和评分规则，冻结正式版本后再安排批次；当前批次是串行调度，支持的自动评分类型以实现为准。
4. 更新[公开测试集候选](../../docs/公开测试集候选.md)、[评测总看板](../../docs/五款产品评测总看板.md)及必要的专项检查记录；验收完成后的发现写入评测总结。

```text
测试集 / 版本 / commit / 许可：
题目 ID / 原题链接 / 本地 case 路径：
评测目标 / 原环境与改编：
输入、提示词、产物及 SHA-256：
官方评分 / 本地评分器版本 / 规则差异：
四产品入口、人工操作和接入状态：
各产品可用 Trace、证据路径和覆盖缺口：
评分器正负例及校验结果：
试跑 run ID、评分和遗留问题：
状态：待准备 / 预实验可运行 / 已试跑 / 正式条件已冻结 / 阻塞
```
