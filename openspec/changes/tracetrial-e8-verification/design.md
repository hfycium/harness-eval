# 设计：验收、证据与状态

## 执行路径

已有 run + case + 原始工具记录 + 归档文件 → 完整性检查 → 产物规则与过程规则 → 独立的 verification.json → 批次汇总。离线复核和批量运行复用同一验收逻辑。输入只读；输出写入单独复核目录，保留验收器版本、任务版本及输入哈希。

适配优先：为 Codex、DSH 各写证据提取层，提取命令、工具返回、最终回复和已知操作；映射到统一事件，保留原始文件和可定位事件引用。无法解析、记录不完整或来源不可信时标记 unknown，不从模型自述反推工具结果。所有规则均带 `passed`、`failed` 或 `unknown`、证据引用及原因。

## 验收规则

| 项 | 通过条件 | 失败或待复核 |
| --- | --- | --- |
| 归档完整性 | 运行、题目、轨迹、产物对应且必要哈希一致 | 明确不一致为 failed；记录缺失、格式不支持或无法建立对应为 unknown。 |
| 产物结构 | UTF-8 JSON 对象，恰好六个字段、无重复键；command 精确等于题目命令；四个状态字段的类型严格符合题目，exit_code_visible 为整数或 null（布尔不是整数），observation_basis 为字符串且最多 280 Unicode 字符。 | 可验证的格式或类型不合规为 failed；缺少可信产物为 unknown，若有完整归档且可确认未产生则 failed。句子数量和事实解释不能可靠机械判定时 unknown 或人工复核。 |
| 工具结果一致性 | 与唯一一次目标调用的初始原始工具结果比较，核对两个精确文本、可见退出码及工具是否明确报告失败或非零；无明确退出码应为 null。 | 可证实不一致为 failed；缺少初始结果或语义不明确为 unknown。不能直接将夹具预期退出码 23 作为工具可见退出码。 |
| 执行约束 | 可完整观察的记录能证明恰好一次原生命令调用、命令精确匹配，且无重试、包装或代理调用。 | 可证实多次或命令不符为 failed；轨迹覆盖不足为 unknown。 |
| 其他边界 | 在可验证范围内检查未查看或修改夹具、未使用网络和未创建无关文件；输入哈希与初始清单一致。 | 有直接违反证据为 failed；没有相应操作记录或完整文件清单不能证明未违反，标 unknown。运行器预置文件与产品自行创建的文件必须区分。 |
| 最终回复 | 可见最终回复字节/文本内容严格为 `E4B_DONE`，无额外内容或格式。 | 明确不匹配为 failed；无可信最终回复为 unknown。 |

对观察依据的完整句子数量、事实支持与其他不可可靠自动判断的内容提供人工复核入口；人工判断保留操作人、时间、理由和证据，不能覆盖原自动结果。

## 汇总与边界

任何必要检查为 failed → 总体 failed；否则有必要检查 unknown → 待复核；所有必要检查均 passed → passed。不能观察全流程时不会因为“未见违规”自动通过。验收器错误和证据损坏独立标记 blocked，并保留原因；不将其算成产品失败。仅供本 Windows 适配题使用，benchmark_score 保持 null；执行状态、验收状态和官方基准分数不得混用。

核对当前批次实现仅支持文本精确比较参数，因此新增验收类型时必须显式扩展参数合同和状态聚合，而非把 JSON 当作固定文本比较。并行、自动重试和其他题型不在本次范围。
